# Incremental build acceptance blocks

Current implementation: [BUILD.md](../BUILD.md). This document retains the broader target design/backlog.

Status: proposed — this matrix specifies future evidence; it is not a list of tests run for this plan.

## Evidence rules

A complete evidence record identifies source inputs, command/rule/toolchain,
platform/ABI, dependency artifacts, actual outputs, selection reason and whether
a target executed or reused a prior result. Case count is not proof of coverage.

Do not add another mandatory whole-tree validation cycle to every edit. Use the
minimum affected targets during implementation, and complete candidate acceptance
at a release boundary. Repeated successful checks with unchanged inputs need no
new run unless the acceptance scope changed.

## Blocks

| Block | Intent | Essential cases | Consumers affected |
|---|---|---|---|
| B01 Graph/input coverage | Every relevant change has an owner/action | New/deleted/renamed JS/guide/schema/fixture; dynamic import/resource; unknown file is explained, never silently ignored | Generator, tests, CI |
| B02 Cache identity | Reuse only equivalent inputs | Same content with changed mtime; changed content with restored mtime; command/rule/flag/toolchain/ABI change; corrupt/partial output and concurrent source edits rejected | All cacheable targets |
| B03 Pure generation | Build reads only declared source/tool inputs | Import/help has no effects; read-only checkout; deterministic generated bytes; no-op output not rewritten | Workspace, reference, kits |
| B04 Rust boundaries | Independent edits stay independent | Guide-only, SDK-only, host-only, core-only; new guide membership; feature/lock change | Core/host/Ops/SDK tests |
| B05 Verification truth | No false current pass | Changed binary invalidates old result; missing/skipped/not-selected distinct; shared-fixture isolation; stale environment rejected | Feature audit, developer/CI summaries |
| B06 Platform artifacts | Final binaries work in their runtime | Bookworm-compatible ELF/stdlib, bundled SQLite/ring/proc-macro build; four-binary image/kit identity; no borrowed host binary | Images, installer, native fixtures |
| B07 Release provenance | Reuse components without lying about source/version | New release/same component; changed guides; old updater/status compatibility; interrupted assembly/resume; no numbered overwrite | Status, guides, release/update/rollback |
| B08 Local/live effects | Build caches cannot replace operational checks | No implicit install/credential/Job action; Docker/live acceptance remains uncached; explicit affected update with active Jobs | Host/installer/operations |
| B09 Cross-repository boundary | Correct server/client/adapter pair | Exact client archive SHA; resolved server commit; Pale engine vs adapter changes; deterministic wheel/ZIP/bundle | Pale, Loom-Use, native MCP |

## Change-to-action matrix

Run these as controlled changes in a disposable tree/output root; restore the
source change after each scenario. Verify action logs as well as outputs/timing.

| Scenario | Work expected | Work that must not be claimed/repeated unnecessarily |
|---|---|---|
| Identical tree/configuration | Graph/identity checks; valid cached targets reused | Recompile, regenerate changed bytes or rerun hermetic tests without cause |
| Workspace CSS | Workspace generation, its UI/source checks, web packaging if requested | Transactional core/host/SDK compilation; native execution suites |
| Guide prose | Guide/reference asset and guidance/packaging checks; composition if embedded | Host/SDK/domain compilation; DB/execution acceptance unrelated to guide delivery |
| Shared API schema | Contracts, handlers, generated reference and actual UI/client protocol consumers | Treating prose-only tests as schema/behavior acceptance |
| Job/recovery implementation | Core/native behavior and real dependent protocol/UI tests | Reusing tests of a different executable as if they covered the new one |
| Host wire/security primitive | Host plus core/Ops actual consumers and rejection/restart cases | Reusing accepted host effects without rechecking actual boundary |
| SDK source | SDK binary/source kit and real producer protocol acceptance | Unrelated core implementation compilation absent a declared semantic dependency |
| New/deleted input | Correct graph/generator invalidation and target membership check | Passing because only the previous file list was fingerprinted |
| Test/helper/fixture only | Its real test target/class/file and dependencies | Reusing a result produced by the previous fixture/harness |
| Compiler/flags/libc/base/browser changes | Rebuild/retest affected platform/env targets | Cross-platform cached results with only a source hash in common |
| Numbered release envelope only | Assembly/provenance/status compatibility checks | Reporting a new source build identity for unchanged old binary bytes |
| Actual deployment/restore | Fresh target-specific readiness/preservation checks | Reusing old health/drain/storage observations as current |

The CSS/guide exclusions describe the end-state separation, not current behavior.
Before provenance/contracts are separated, record necessary extra actions honestly
rather than suppressing them to match a desired benchmark.

## Safe concurrency

Use only measured independent action parallelism. Preserve process/fixture
isolation and bounded concurrency for browser sessions, SQLite writers and Docker.
An execution timeout/cancellation assertion must not be loosened just to make a
parallel run pass. Use resource classes/pools and keep per-case failure evidence.

## Cache and audit acceptance

- A single old successful suite flag cannot qualify a new mixture of evidence.
  Validate each required target's inputs and exact consumed artifact/environment.
- A partial/developer run reports partial coverage. A full release plan accounts
  for every required target, with reused versus freshly executed evidence explicit.
- Local Docker and live checks have fresh acceptance records independent of
  hermetic cache completeness. No GPU/Sim success is inferred from CPU fixtures.
- Test refactoring preserves invalid-input, permission, state/fault/restart and
  source-preservation cases. Delete duplication only after the replacement is real.
- New build tests should mutate representative inputs and inspect actual action
  sets/outputs. Avoid dozens of checks merely asserting source text/BUILD spelling.

## Pilot go/no-go

Proceed to wider Bazel migration only when the representative native/web/protocol
pilot builds from clean inputs, preserves behavior, rejects undeclared dependencies
and produces correct warm action sets. Compare total time/overhead against the
improved Cargo/BuildKit baseline. If benefits disappear after P1/P2 fixes or rule
maintenance dominates, retain that simpler baseline and record the result.

No numeric success threshold has been fabricated from the previous full-suite
record. Establish one after P0 measurements, before evaluating the pilot outcome.
