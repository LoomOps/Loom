# Scientific outputs and experimental setup

Status: proposed. Design for review against the native development tree. The field names, Setup references and admission checks proposed below require implementation. The installed reference remains authoritative for current actions.

## The unit of analysis

The [implementation boundaries](OUTPUT-IMPLEMENTATION.md) specify field authority, admission and publication behavior, read projections, historical adoption and acceptance checks.

A Job owns a requested outcome. An Output revision is a reusable record of what was produced, how, under which conditions, and with what observations. Its baseline coverage follows from the output kind and activity. The same baseline serves an exploratory run and a run with a hypothesis. An author can run an experiment, inspect the results and form an impression afterwards.

| Object | Stable record | Boundaries |
|---|---|---|
| Dataset | Population, membership, derivation, splits, observations, labels and collection conditions | A new randomized rollout and a transformed view of an existing rollout have different lineage. |
| Policy, including VLA | Exact checkpoint, training inputs, inference interface and selection record | Training and validation belong to the Policy. Each deployment evaluation owns its rollout measurements. Keep the wire kind `model` and the policy role. |
| Evaluation | Exact evaluated controller, population, Setup, procedure, case observations and outcomes | A descriptive evaluation can record what happened with no predicted outcome. A protocol may define trial success for reporting its frequency. |
| Task | Behavior or goal shared across Jobs | Dataset parentage, checkpoint lineage and comparable evaluation conditions each need their own exact references. |
| Experimental Setup | Physical, sensing and control configuration | A Dataset can span several Setup revisions. A Policy can be evaluated in a Setup it never encountered in training. |

### Optional hypothesis at Job submission

An exploratory Job submits its deliverables and ordinary activity coverage. Loom-use does not ask the author to invent a hypothesis, choose a direction of effect or supply a threshold to proceed. For an exploratory closed-loop rollout without a scoring rubric, provide a descriptive protocol covering the procedure, scheduled and observed trials, Setup bindings, observations and trace references. A scored evaluation binds its metric and scoring rule even when no particular result is predicted.

When the caller supplies a hypothesis, Loom-use adds a prospective analysis contract **when the logical Job is first submitted**. Freeze the hypothesis statement, relevant deliverable aliases, factor and conditions, intended cohort, metric or observation rubric, analysis/comparison rule, applicable exclusions and required evidence references or selectors. Quantitative tests can specify an expected direction or threshold and uncertainty method where appropriate. The contract adds to the applicable baseline. Publication checks that the promised analysis was performed; an effect opposite to the prediction is a valid result.

An open Job awaiting a Runtime freezes the same scientific commitment at creation. Later plan revisions may bind a compatible Profile or reporter. A missing commitment for a declared hypothesis fails submission; a binding that weakens it fails revision. Observations made after inspecting results may be attached as dated interpretations linked to the exact Output and evidence. A new hypothesis prompted by those observations can be submitted on a linked follow-up Job. The original submission history retains the distinction.

## Where the existing implementation helps and where it stops

The metadata registry already provides exact pins, extension schemas and typed display fields. Reporting already has five built-ins: Dataset membership, SDG membership/conditions/readback, native Policy training, Policy import and Evaluation cases. Profiles bind exact revisions, capabilities and expectations. Publication checks report hashes, producing Job/Attempt, relevant inputs and domain invariants. The Rust producer writes report components and the Dashboard reads bounded pages. Preserve these paths. [Metadata registry](../../rust/contracts/metadata-templates.json) · [Reporting resources](../../rust/contracts/reporting.json) · [Native verifier](../../rust/crates/core/src/reporting.rs) · [Output viewer](../../dashboard/workspace/reporting.js)

Three specific overlaps motivate this proposal:

- Metadata exposes `/physics/physics_hz` and `/physics/control_hz`. The evaluation protocol separately declares `scope.physics_hz` and `scope.control_hz`. There is meaning in both an expected rate and an effective rate. The present fields alone cannot identify a shared physical setup, compare configurations across sessions, or establish measured timing.
- Metadata exposes evaluation counts and splits. Report verification already has case counts, membership and split reconciliation. The built-in case path requires a success-ratio primary and emits “Whole-task success.” Continuous offline metrics such as held-out action RMSE need a distinct result family with its own numerator/aggregation semantics.
- Both metadata fields and report requirements can carry display descriptors. The existing reporting specification distinguishes schemas, definitions, coverage and views. Complete that design with an explicit authoritative source per **semantic field and role**, and a single list/detail projection. [Existing reporting design](REPORTING-CONTRACT.md)

## Ownership and permitted overlap

| Layer | Owns | Example |
|---|---|---|
| Metadata template | Identifiers, semantic field types, units, cardinality, accepted missing states, structural extensions and catalog display bindings | A Dataset exposes accepted episode count and split counts. |
| Definition / protocol | Meaning of a factor or metric, frame, denominator, population, estimator, case validity, success predicate, evaluator and permitted controller/GT access | XY spawn in table coordinates; valid-trial success within a specified tolerance and hold duration. |
| Experimental Setup revision | Versioned physical configuration, calibration and timing baseline with domain and evidence provenance | Which wrist camera, transform revision and controller configuration a session used. |
| Report contract | Activity-wide evidence, applicability rules and validation, plus any analysis committed at Job submission | SDG requires target and observed XY coverage using the same factor definition. |
| Producer report | Actual values, case/member identities, checkpoint, session binding, exclusions, timestamps and source components | Counts and measured XY values of accepted and rejected cases. |
| Catalog / Dashboard view | Which verified fields appear on a row, detail, chart or comparison; read pagination and missing/conflict display | The row shows accepted episodes; the distribution panel groups those same members by split. |

Use a qualified binding such as *accepted episode count → membership report → count*. Its descriptor names the exact requirement, versioned field identity, pointer, unit and aggregation. Materialize a small, reproducible projection keyed by output revision and projection version. References spanning outputs retain their original source revision. Reordering UI fields only changes the view. Reinterpreting a unit, denominator or frame requires a new definition and compatible contract revision.

**Allowed overlap:** a protocol may prescribe 30 Hz; a Setup may configure 30 Hz; the session may measure 28.9 Hz. Give these distinct roles and evidence pointers. A metadata field may cache a report summary with a source digest. Two authors supplying the same semantic fact independently require equality after declared unit conversion, or a publication conflict for new data. For historical disagreement show both sources and the conflict. Never resolve by preferring the newer timestamp or the more attractive value.

## Minimum coverage by activity

“Required” applies within the selected activity. A conditional requirement becomes mandatory when a frozen applicability predicate is true. Optional evidence can support later analysis. A Job can commit to specific additional evidence at submission, making it required for that Job. Old sources and external imports have explicit evidence levels. The following are proposed defaults for new native production.

| Activity | Required | Conditional | Optional |
|---|---|---|---|
| Dataset collection or derivation | Exact source demos/parents or original acquisition session; transformation for derived members; robot and Task where applicable; episode identity, split policy/counts and zero/missing distinction; observation and action schema with channels, units and frames; Setup coverage by session or member | SDG declares intended factors, distribution/support, seed or reset identity, then reports attempted, accepted, rejected and actual readback by split. Paired physics variants preserve pair IDs. Language-labeled data declares stored text/assignment and annotation source. Claims of held-out generalization require a leakage check on the split unit. | Extra factor correlations, illustrative frames and episode lengths where useful for inspection |
| Native policy training | Exact training and validation Dataset revisions/splits; base and selected checkpoint identities; preprocessing, sensor order, action channel order/units/frame/representation, normalization fit split; checkpoint selection criterion, step and measured train/validation series over the declared schedule | Language-conditioned VLA records the exact consumed instruction set, assignment/phase, formatting and coverage. Action prediction using continuous comparable targets reports held-out errors per channel with normalization and units. A hybrid controller records which phases used the Policy. | Additional metrics, ablations, per-condition validation and resource curves unless promised in the Job |
| Policy import | Checkpoint digest, source, compatible interface, known input/output and conditioning evidence plus provenance level | Attach training lineage, selected step and curves when supplied with verifiable sources. Unknown history stays visible. A claim about validation or checkpoint superiority requires supporting evidence. | Additional upstream training artifacts |
| Closed-loop evaluation | Exact Policy/checkpoint or declared controller stack, Task and test population/reset source, protocol/evaluator pin, Sim/Real Setup binding, validity/exclusion rule, per-case observations/outcomes, and interruption or failure reasons. Descriptive protocols expose case counts and trace references. Scored protocols declare their primary metric. For binary success keep planned, run, valid, success, task failure, infrastructure failure and pending counts with explicit accounting. | Hybrid control records phase ownership and which party used GT. Robustness claims require per-factor results and denominators; transfer claims require the comparison rules below. If the current Profile requires a Dataset input, supply its exact revision. Proposed live Real trials may instead pin a typed reset/cohort manifest under a dedicated contract. | Diagnostics, trajectories, videos and secondary success criteria |
| Offline evaluation | Exact Policy, held-out Dataset revision/split, sample population, target channels, metric/units, aggregation, result and excluded samples | Continuous action error reports per-channel values and normalization. A discrete prediction task can define its own primary metric. A transfer claim must identify data domains and acquisition setups. | Error histograms, phase breakdowns and calibration curves as applicable |

Robot mechanical DoF, controlled DoF and action-vector dimension are distinct. A gripper command or pose representation can change vector dimension without changing mechanical DoF. Report MSE in squared units and RMSE in original units. A Dataset annotation, the generator prompt, the training instruction and the instruction actually used in an evaluation are four separate roles. Keep exact text or an immutable, inspectable instruction-set reference with case assignments. A Policy without language conditioning can legitimately record that fact.

## Experimental Setup and Sim–Real comparison

Use **Experimental Setup** as the domain object and **Setup** as the compact UI label. **Scene** is one section for assets, layout and initial conditions. **Simulation** covers simulator-specific fields. Runtime continues to own executable software and its dependency pins.

| Section | Fields and evidence |
|---|---|
| Scene and embodiment | Asset and robot-model revisions, tool/end effector, payload, object variants and geometry, workspace, base/table/task frames, reset procedure. Randomization bounds belong to the factor plan; actual samples belong to the episode/case report. |
| Sensors and calibration | Sensor identity and mount, modality, resolution/crop, depth scale, intrinsics/distortion, directed extrinsic with frame names, units and axis convention. Pin calibration artifacts, method and acquisition time; record residual/uncertainty and validity interval where available. In Sim distinguish authored camera geometry and injected noise from physical calibration. |
| Control and time | Control mode, actuator configuration, commanded control rate, policy inference/replan and action execution cadence, sensor sampling and recording cadence, synchronization/clock domain, measured latency/jitter/dropouts where relevant. Compare like quantities. |
| Simulation | Simulator/backend and exact build or Runtime reference, physics `dt` in seconds, solver, substeps, decimation convention, gravity, contact/friction/material model, render interval and noise/randomization revision as applicable to the claim. Define whether a “substep” subdivides a physics step. Publish derived Hz with its formula. |
| Real hardware | Hardware/firmware and controller revisions where relevant, sensor serial or stable inventory alias, calibration session, physical measurements, acquisition timestamps and controller telemetry. Real physics-step rate is inapplicable. A measured control loop or camera rate has its own field. |

A reusable **Setup revision** is an immutable typed manifest with ID/revision/digest. A **session binding** identifies the exact Setup, its role (collection, source acquisition, evaluation), the Job/Attempt when present, the member/case range, and evidence of what was actually applied. If a camera moves or calibration changes, begin another binding at that boundary. One mixed Dataset carries a mapping and coverage counts. A Policy follows training Dataset acquisition bindings by lineage and separately declares inference assumptions. Training device/software and evaluation apparatus have different owners.

Record configured, effective-readback, measured and derived values explicitly. Evidence includes units, clock or frame, collection method, source component/digest/pointer and the population or time window it describes. Large transforms, calibration files and timing traces stay in registered components. A digest verifies identity; fit quality and acceptable error come from a protocol criterion. Sim `dt = 1/120 s` and control decimation 4 imply nominal **30 Hz** under one control step per four physics steps. That arithmetic provides no measurement of a real controller, inference cadence or camera. This distinction follows the environment time-step semantics in [Isaac Lab](https://isaac-sim.github.io/IsaacLab/main/source/api/lab/isaaclab.envs.html).

**Comparison rule.** Select two exact Evaluation revisions and a comparison specification. Specify each comparison axis as held constant, deliberately varied, domain-specific or informational. Match Task/criterion, selected checkpoint, controller phases, metric definition, population, frame mapping and evidence grade before computing a headline delta. Use per-field outcomes *matched within declared tolerance*, *different*, *unknown* and *inapplicable*. A declared Sim→Real change is expected. An unmapped goal frame or changed success denominator blocks the headline delta while keeping both outcomes inspectable. Match cases only using a declared pairing key; independent cohorts retain separate denominators, uncertainty methods and sample sizes. Missing real calibration limits a calibration-controlled claim; it need not invalidate a standalone real evaluation. A measured gap under several simultaneous changes describes an association; attribution requires an appropriate experimental contrast.

Record the factors actually varied and the conditions actually observed, including on exploratory runs. A hypothesis can additionally prescribe a comparison along one of those axes. LIBERO-Plus varies, among other things, viewpoint, robot initial state, object layout and instruction. For a Chalk placement experiment, XY and orientation in an explicit table frame can be primary while episode length stays secondary. SIMPLER separately investigates visual matching and system identification; this motivates distinct visual/calibration and control/dynamics comparison axes. These sources inform the design choices. [LIBERO-Plus](https://openaccess.thecvf.com/content/CVPR2026/papers/Fei_LIBERO-Plus_A_Progressive_Robustness_Benchmark_for_Visual-Language-Action_Models_CVPR_2026_paper.pdf) · [SIMPLER](https://simpler-env.github.io/)

## Loom-use decision and publication flow

1. Inspect the nearest comparable record by task, modality, activity and protocol. Record its exact revision as a format reference. Resolve baseline requirements from the output kind, activity and applicable conditions. If the caller states a hypothesis, identify its additional evidence before submitting the Job.
2. Reuse the metadata template, definitions, Setup and report contract independently. A new calibration/configuration needs a Setup revision. A new measured quantity or denominator needs a definition and contract that consumes it. A new required analysis or justified exclusion needs a derived contract. A new searchable/displayable property needs a typed metadata extension/binding. A change of chart layout only needs a view change. A new metric intended for the main list can require both a contract and a metadata binding; use a single measurement source.
3. Preview the effective coverage per promised output. Proposed preview returns included/conditional/optional/excluded requirements, responsible reporter/evaluator, accepted inputs, planned Setup constraints and missing capabilities. At submission freeze the activity coverage and, when present, the hypothesis contract on the logical Job. The current `jobs.create` deliverable binds an alias and kind; carrying an immutable scientific contract reference at this boundary is proposed. An open Job may defer executable Profile binding until installation. At binding, verify that the Profile can fulfill the original commitment before dispatching the affected Node.
4. Exclusion/replacement requires reason, exact evidence, applicability predicate and impact on the claim. A missing implementation for applicable evidence is an authoring gap. Resolve that gap before submission or use a new Job for a revised scientific commitment. A required measurement that fails during a run records an incident and blocks publication under that claim. Use existing publication repair where the underlying bytes suffice; a truly unmeasured quantity needs a new measurement. Zero successes with valid trials is a publishable result. Zero valid trials yields an undefined rate and a preserved failed/inconclusive evaluation record under the declared protocol.
5. Produce typed reports and session bindings. At publication verify exact pins and source bytes, populations, attribution, units/frames, applied Setup, and consistency between compact projections and the reports. Preserve original Job/Attempt on replay. Legacy imports retain Missing, Not measured or Not applicable with source provenance; an operator annotation cannot acquire the assurance level of a measured run.

## How this reads on the Dashboard

Keep the current Outputs navigation. Use the same projection for MCP, the list and the detail header. Present Task and exact lineage near the title; expose Sources and contract exceptions on demand. Use the protocol’s primary metric when scored. For a descriptive rollout, show the observed trial count and access to representative traces. Place post-run impressions with their evidence and timestamp. Page detailed values through the existing bounded-report paths.

| View | List row | First detail view |
|---|---|---|
| Dataset | Accepted episodes, observed modalities, split, observed variation where recorded | Parent/derivation and target-versus-observed coverage by split, with units/frame and exclusion counts. Select Setup by acquisition session. |
| Policy | Architecture, observation/action interface, selected checkpoint | Exact training Dataset/split, consumed instructions and selection evidence. Drill into phase/split loss, metric definition and channel errors. |
| Evaluation | Observed trial count or primary metric with units or numerator/denominator, scope and domain | Policy and cohort links, success predicate or continuous estimator, evaluator, Setup, invalid-case counts, factor-stratified results. |
| Comparison | Selected evaluation revisions | Show population and Setup differences before the metric delta, including the reason for each unavailable comparison. |

**Illustrative path.** A parent demo yields an SDG variant varying object XY. The child Dataset binds each accepted case to its source and actual XY. Its VLA Policy links the trained split and exposes the text assigned to that split. Two rollouts select the same checkpoint, one in Sim and one in Real. A changed wrist-camera transform shows up in the Setup comparison. The reader can follow the transform to the calibration file, inspect both case populations and decide whether the claimed transfer comparison is supported. No operational records or measurements are assumed by this example.
