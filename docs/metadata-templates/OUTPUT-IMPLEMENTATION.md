# Output evidence implementation boundaries

Status: historical implementation and rollout record. See the [Results feature specification](../features/results.md) and [reporting guide](../../loom_use/reporting.md) for supported behavior.

## Current implementation

The [authoring guide](../../loom_use/reporting.md#outcome-commitments-and-sessions)
defines the wire format available in the development candidate.
`jobs.preview_outcome` resolves the evidence requirements. `jobs.create` freezes
the scientific commitment and digest, and plan revision binds each producing
node to the accepted Profile pins. Publication verifies explicit population,
session and analysis evidence against the pinned Job and Attempt. The Dashboard
shows accepted reporting, applied setup and bounded readbacks, and preserves the
existing comparison compatibility checks. The sections below retain the broader
design for legacy adoption, independent measurement definitions and future
projections.

## Acceptance target

A reader can start at a Dataset, identify the exact Policy revision trained on it, and inspect a case from an Evaluation of that checkpoint. At each step the reader can tell what was configured, what was measured, by whom, in which population, and where the value came from. An exploratory Job can complete this path without a hypothesis. A Job submitted with a hypothesis can show the original promise next to the analysis actually delivered. Both paths use the same baseline for the same activity.

The private review sample exercises one existing chain. Its historical records illustrate display and adoption. Native authoring, exploratory admission, hypothesis freezing and comparison of two matched physical sessions require independent fixtures.

## 1. Define who supplies each value

| Semantic field | Authority | Identity and mandatory qualifiers | Projection and failure behavior |
|---|---|---|---|
| Dataset population, splits and parent | Membership report with source member IDs and derivation links | Dataset revision, member ID, split rule, inclusion status, parent revision when identified | Count distinct accepted members. Preserve a recorded parent label when its revision is unknown. Do not connect by label. |
| SDG variation | Condition assignments for requested variation and producer readbacks for realized variation | Case/member ID, factor definition, unit, coordinate frame, stage/time of readback, split | Two independently selectable series. Compute ranges only over observations with values and expose the measured denominator. |
| Language | Dataset annotation, Policy training input mapping or Evaluation prompt, according to role | Exact text/source revision, assignment unit and split or case when known | Show actual wording in the applicable view. A processing/configuration name cannot satisfy a language requirement. |
| Policy selection | Checkpoint artifact and producer selection report | Training Job/Attempt, candidate checkpoint or step, criterion, split, selected step and total updates | Separate selected checkpoint from final update. Cross-link a sibling report only with an unambiguous output binding. |
| Policy error | Versioned metric definition and held-out or validation observations | Phase, split, update, axes, scale/normalization, aggregation, unit per channel | Training objective, normalized validation loss and physical-unit test error retain independent labels. Action width is required for per-channel errors. Robot kinematic DoF is a separate field. |
| Evaluation observations | Evaluator case report and pinned procedure | Tested policy, dataset/reset cohort, protocol revision, scope, invalid/smoke cases, evaluator version | Show case observations for descriptive runs. For scored runs derive the declared primary from eligible cases using the declared estimator. Surface contradictions. |
| Setup | Declared revision, session application receipt and measured readback | Sim/real domain, validity interval, component version, units, frames, clock and calibration evidence | Distinguish requested rate, effective configuration and measured timing. Expose gaps by session, including missing Real linkage. |
| Initial commitment and later interpretation | Accepted root Job submission and subsequent append-only annotation respectively | Job ID, deliverable alias, commitment digest, author/time, cited Output revision and cases for an interpretation | Historical absence of a commitment means unrecorded intent. The outcome of a test does not affect whether its reported analysis is complete. |

For each promoted field keep a qualified source pointer (revision, component, digest, JSON pointer or row selector), semantic role and evidence status. Use explicit statuses for present, unrecorded, not measured, inapplicable with reason and conflicting evidence. Preserve numeric zero. Never average unlike units, cohort definitions or coordinate frames. Require an explicit versioned conversion where definitions allow it.

## 2. Authoring and admission

### Missing evidence across activities

Resolve coverage from kind, activity and declared conditions regardless of which fields appear in a historical example. Use the following read contract for each applicable catalog field. A present value has a typed value, source and observation role. For an absent value return a null value, stable status, reason when known and the scope inspected. A missing value in the selected manifest does not establish that the instrument never measured it. If a referenced source was unavailable, attach its access/read failure to the inspection and keep the measurement status unknown. An optional calculated statistic which has not been computed must not erase its available underlying observations.

| Case | Read result | New Job behavior |
|---|---|---|
| No record of a value in the inspected sources | `missing` with inspected scope | Optional fields may remain missing. An applicable, promised measurement needs evidence before verified publication. |
| Producer explicitly records that measurement was skipped | `not_measured` with attributable reason | Accept for optional evidence. A promised measurement still fails coverage. |
| Field is irrelevant to this activity | `not_applicable` with applicability rule | Apply an existing conditional rule or pin a justified contract variation at submission. |
| Sources disagree on the same measurement | `conflict` with exact competing references | Report a field-level conflict. Require repair for a claimed metric that depends on it. |
| Valid observation equals zero | `present` with value 0, source and denominator when relevant | Publish normally. Zero valid trials leaves a rate undefined and preserves the observed trial count. |

Loom-use exposes applicable gaps in the draft preview together with the required reporter or proposed contract extension. Read responses and archived rows can always represent missing evidence. The writer checks the accepted contract. A quality review can group gaps by activity, semantic field and reason to identify problems in guidance or reporter capability. A frequent gap calls for investigation before promoting a field to universally required. Test matrix: recorded demonstrations without SDG randomization, SDG with measured perturbations, language-free policies, imported policies without training history, continuous offline evaluation, descriptive real rollouts and scored simulation cases.

**Registry.** Extend `rust/contracts/metadata-templates.json` and `reporting.json` through new revisions. Templates select exposed typed fields and reusable presentation elements. Definitions own measurement/protocol semantics. Report contracts own applicable evidence and checks. A user-created contract may extend a built-in, replace a requirement with a justified alternative, or exclude a genuinely inapplicable requirement with a predicate and evidence. Changes to chart layout need only a view revision. A new physical measurement may need a definition, reporter and contract as well as a display binding. Archive keeps existing pins resolvable.

**Root commitment.** Extend `rust/contracts/job-contract.json`, the typed domain and the native plan writer. Proposed optional `outcome.science` has a version and a mapping from stable deliverable aliases to activity, exact template/evidence-contract pins, applicable definition pins, input selectors and Setup constraints. Exact evidence artifact references do not exist at submission; freeze the selectors and expected output bindings then resolve them at publication. A Policy transfer test may bind several deliverables to one optional hypothesis. The hypothesis carries its statement, factors, cohort selection, metric or observation rubric, analysis rule, exclusions, required evidence and any direction specified by the author. No scientific block is needed for an ordinary non-scientific artifact. No intent classifier is needed.

**Admission transaction.** Share one canonical validator across logical Job creation and direct or workflow submission for new covered activities (`plans.rs`, `jobs.rs`, `reporting.rs`). On the first successful submission persist the normalized commitment and digest in the same transaction as the logical root. Accept a covered exploratory Job with baseline and no hypothesis. An open Job may defer exact Runtime binding. Reject a declared hypothesis with no analysis plan before allocating execution. Plan revision checks the frozen digest and stable deliverable identities. A later bind proves Profile/reporter compatibility and preserves the commitment. Retry, recovery and publication repair read the same root digest. An outcome change after data inspection starts a linked follow-up or dated annotation. A changed scientific promise cannot masquerade as a retry.

**Caller contract.** Add a proposed read-only coverage preview to the native action registry for both MCP and HTTP. Input is a draft outcome, pins and optionally Profile. Return per-alias applicable, conditional, optional and justified exclusions, missing reporters and stable field errors. Preview is advisory; submission validates again transactionally. Return a structured conflict with the affected alias, field and accepted digest on an incompatible revision. Keep authorization and concurrency behavior consistent with the corresponding existing read, submit and revise paths.

## 3. Setup, producer evidence and publication

Use the item/revision registry and registered file inventory for immutable Experimental Setup manifests. A Setup records common properties (robot/controller, sensors, clocks, frames), plus Sim settings (engine, physics step, solver, randomization) or Real settings (hardware/firmware, calibration validity, measured timing). Introduce scoped register/revise/read operations or extend the existing registry actions where semantics match. Read follows existing item visibility; writes require corresponding management rights. Archive preserves historical lookup. A revision change to a camera calibration creates a new identity binding for the affected sessions, even inside one Dataset. A sensor replacement needs a new calibration reference even when the nominal intrinsics match.

A producer binds a session or case range to the applied revision and supplies readbacks with their own timestamps, frames and source digests. A range boundary must be resolvable to exact members/cases. Reject ambiguous overlapping assignments for the same role. Unmatched Real sessions leave a comparison incomplete. No device operation is necessary to register a manifest. Implement producer support in `rust/crates/sdk/src/lib.rs`; collection adapters and evaluators supply the measurements they can observe. The scheduler owns execution and the Runtime identifies runnable software. Neither can attest to physical measurements on its own.

At publication use the existing verified result transaction in `results.rs` and report validators in `reporting.rs`. Resolve each promised alias and its evidence, verify revisions, component hashes, Job/Attempt association, roles, units, split membership and declared protocol. Several Policies from one Attempt require explicit report-to-checkpoint subject references. Reconcile denominators against scheduled, eligible, observed, smoke, excluded and invalid cases. A descriptive procedure can publish observations without a score. For a scored protocol, zero eligible cases has an undefined score; retain the case report and its inconclusive status. A valid measured result opposite to a stated hypothesis passes. Block a new claimed result with missing required evidence; preserve diagnostic evidence and allow repair from existing immutable files. An unavailable measurement requires new evidence.

## 4. Read model, Dashboard and comparisons

Build the compact read projection in native Core using `metadata_templates.rs`, `research_metadata.rs`, `results.rs` and `catalog.rs`. Index only row/header data and exact links. Key a projection by output revision, projection schema revision and evidence-set digest including selected overlays, Setup bindings, report digests and definitions. Compute and replace atomically on publication or adoption. Detect stale dependencies on read or during reindex. Lists never open tensor archives, case files or an entire timeseries. Reuse bounded `results.read_report` and `results.get_report_evidence` for detail and existing authorized file lookup for raw material.

| View | List / first detail | Drill-down and boundary |
|---|---|---|
| Dataset | Task, lineage, accepted count, split and observed modality | Derivation tree, condition distribution by split, configured vs observed toggle, units/frame, coverage and source. Multiple parents remain links. |
| Policy | Trained-on Dataset revision, architecture/interface, checkpoint selected | Exact instructions, validation steps and phases, per-action channel errors in native units, selection/test separation, checkpoint provenance. |
| Evaluation | Dataset and Policy links, domain, protocol, eligible cases and declared primary if defined | Read the decision rule before interpreting the number. Filter cases, inspect failures, intervals and clocks, see all recorded metrics and evidence. |
| Setup / Comparison | Context link on each Output and selected session | Compare domain, calibration, frames, frequencies, cohort and protocol. Permit descriptive inspection with differences visible. Calculate a formal delta only if its required comparison keys and definitions match. |
| Job detail | Effective deliverable coverage; prospective contract when supplied | Show the frozen version, execution receipts and later interpretations separately with exact evidence links. |

Wire one projection into `dashboard/workspace/{outputs,catalog-pages,research,research-metadata,reporting}.js`. Keep existing navigation. New detail renderers consume typed descriptors (counts, reference, condition series, cases, metrics, Setup difference); restrict them to platform-owned renderers. If the backend cannot supply a verified value, display the supported evidence state. Avoid inferring types or semantics by parsing human-readable labels in JavaScript. Scope larger reads by Output and cursor; cancel requests when selection changes and retain selected tab, split and scroll on refresh.

## 5. Historical correction, consumers and delivery

### Source material for independent analysis

The episodic SDG built-in uses three Dataset tabs: Overview, Distribution and Episodes. Overview places unique collection checks beside membership, calibration details under Simulation, and the parent demo and downstream Policy references alongside the collection. Distribution visualizes population coverage using plots appropriate to the declared randomization factors. For paired X/Y offsets use a scatterplot with equal physical scales and distinguish the splits. Label assignments and measured readbacks independently. A mark links to its member or matching member set. Episode browsing, media and per-member evidence belong in Episodes. This is a template layout decision.

Overview starts with Simulation, then Collection (linked Task, accepted episodes with their split, recorded observations/actions, and frame count qualified by stream or synchronized pair). Show template and contract pins in the Overview footer. Each declared distribution factor has typed values, units, reference frame where applicable, and a sampling unit such as parent placement, entry pose, or full condition. Project paired geometry as a scatterplot, scalar offsets as aligned histograms, categorical variants as counts, and crossed factors as a coverage matrix. A parent or entry repeated across postures must contribute only once to its own marginal plot. Join condition assignments to realized records by stable condition identity. Show assigned, observed, and admitted populations with their own denominators. Keep fixed conditions, unrecorded factors and unexplained absences distinct. A built-in template may opt into any of these views.

Following a condition opens Episodes with the exact Dataset revision and member selected. Where a condition has several members, open the filtered member list. Direct entry to Episodes supports browsing independently of any distribution. Bind counts, timestamps, synchronized camera views and file/member references to that exact episode. Clear frame selection on member change. Keep a member inspectable when its preview is unavailable.

**Distribution authoring.** Ask what coverage a reader needs to verify for this dataset. Start from the generation recipe and declare the intentionally varied factors, their sampling units, dependencies, and the split or cohort used for analysis. Each declared chart identifies its factor definitions, population, grouping or binning, missing-value handling, and a resolvable member-level source. Provide assigned and admitted counts for applicable groups, and record measured values where available. Use one joint view for factors whose combinations affect coverage. Flag empty planned combinations, unexplained exclusions, or a mismatch between planned and retained coverage. Seeds are provenance unless the seed itself defines the comparison. Verify that grouped totals reconcile and repeated children are counted once at the parent level. Use the minimum set of plots that lets the reader check the declared coverage and locate the contributing members. Template-specific charts can be assembled from the shared renderer catalog.

An analyst must be able to start from a displayed measurement, inspect the record that contributed to it, and resolve the exact underlying material for a different analysis. Keep three things distinct: a catalog fact, a bounded sample for inspection, and the complete registered source. A list of archive names or a rendered chart alone does not satisfy a promised reusable source.

| Activity | Sources to bind when applicable | Useful inspection |
|---|---|---|
| Collection and derivation | Member index, parent and transformation recipe, stream schema and timing, calibration, raw observations/actions or a reasoned access restriction | Open one exact episode, show synchronized views with time/tick and units, inspect action/state schema, resolve its archive member and digest. |
| Training and checkpoint selection | Dataset revision and split membership, recipe/config, actual dependency and code pins, checkpoint parts, training series, validation population and selection record | Select an update and inspect the training log row, validation rows by phase and the fixed checkpoint-selection rule. Imported policies can specify which training sources were supplied. |
| Rollout and offline evaluation | Protocol/evaluator revision, per-case reset and cohort, judged observations and decision record; control, physics, sensor or other traces appropriate to the activity | Follow one outcome to the relevant samples, units, clock and scoring rule. A synchronized replay or video is conditional on having actual frames and timing. |

Allow the producer to register each source once and bind its role, subject, exact revision and selector to several measurements. A selector can identify a file or archive member, dataset path and frame range, case ID, timebase or log key. Distinguish source existence, authorized availability, verification and preview availability. A missing thumbnail does not imply a missing episode. Read APIs should page descriptors, support scoped trace windows and return authorized locators for full analysis through the existing file-access route. Preview only allowlisted fields and bounded verified bytes; raw provenance and private logs require the source's existing permissions. Loom-use previews the sources needed by the declared activity before submission. At publication check that the promised sources can be resolved and match their declared role and identity. Historic records can report an unavailable source.

Acceptance: follow an observed value to its source row through API and UI, select another episode/case without leaking the previous subject's preview, and reopen the registered original independently. Test restricted sources, a present file without a preview, unavailable originals, large archives, sparse samples, mismatched clocks and missing source bindings. Keep large files out of MCP responses.

Order the top-level Output categories Datasets, Policies, Experiments. The built-in trained Policy template uses Overview and Training. Overview shows the linked Task, exact training Dataset, input/output interface, chosen checkpoint, and the instructions actually consumed. A compact footer links the template and contract revisions when they are recorded. Show training-critical label semantics inline or in an expandable section: which labels were fed as inputs, which became targets or masks, and how the run transformed or aligned them. The Dataset owns annotation provenance, labeling method, and segment boundaries. The Policy links to the exact sources it used.

Training combines validation curves, training traces, checkpoint selection and offline test metrics in one tab. Use actual optimizer steps on the horizontal axis. Use Subtask for a labeled trajectory segment tied to an intermediate objective. Display the producer's names and definitions where recorded and use numeric identifiers where names are unavailable. Existing producer fields such as phase IDs retain their source names and can map to Subtask in the read projection. A training stage describes an optimization regime such as pretraining or fine-tuning. The Best checkpoint marker comes from the producer's global selection record and stays at that step during subtask inspection. Only mark the global curve as the selected score. Report the current step's subtask loss and population independently. Offline held-out action error retains its own units and population. Evaluation Overview summarizes rollout results. Protocol and Cases carry the executed rule and observations.

The linked Task describes the objective, starting state, scope, intended end state, and relevant objects or reference frames. Include milestones or a default success predicate when defined at that Task revision. Each Evaluation pins the actual protocol revision with numerical tolerances, hold time and validity rules. Dataset authoring records the rule for including examples and the source of action targets and labels. These references let a grasp-only Policy and a planner-assisted alignment Evaluation share a Task family while preserving the scope of each result.

The built-in closed-loop Evaluation template uses Overview, Results and Cases. Overview shows the Task, exact evaluated Policy and Dataset or condition cohort, evaluation scope, primary result and denominator, and the applied protocol with an expandable execution setup. Place Template and Contract pins at the bottom. Results shows the outcome breakdown and plots selected for the evaluation's declared rubric and data. Choose a separate denominator for a check if applicability differs across cases. If several checks can fail in the same case, present them as overlapping observations with per-check counts. A sequential funnel requires verified stage eligibility. A final-state measurement has its own unit and can be compared with the applicable final-state threshold. Whole-task success follows the complete predicate including duration and all other required checks. A plotted case links to the same case in Cases, which provides the individual judgments, relevant traces and source files. Offline and descriptive evaluation templates can select different summaries and plots from shared renderers.

1. **Read support first.** Ship additive definitions and readers. Generate discovery/action reference from native registration, update server guides in `loom_use/{metadata,reporting,results,workflows}.md` and thin Loom-use skill routing. The agent checks comparable records, previews coverage, pins existing definitions or registers justified extensions, then binds a reporter before executing. A previous record provides a format reference, never another run's measurements. Older clients continue reading their original pins. Pale only needs a change if it consumes a changed field or must transmit a newly declared commitment; orchestration and report delivery are outside the evidence model.
2. **Sample adoption.** Extend reconciliation preview and revisioned overlays. Resolve native consumes/produces links, exact component SHA and source pointers. Use the expected field role to choose evidence. A sibling report with ambiguous scope is a review item. Produce an explicit proposed diff per field with prior value, source, conflict, confidence basis and unresolved items. Start with one Dataset, one Policy, one Evaluation and incomplete/mixed Setup examples. Operator applies an approved preview against the same evidence digest and expected overlay revision. Stale preview conflicts; replay of an applied preview is idempotent. Keep original bytes, legacy values and historical Job identity.
3. **Enable new writes.** Version-select new admission and publication behavior for newly declared coverage. Existing accepted Jobs and publications keep their pins. Roll back readers to the preceding projection or disable new admissions independently; retain commitments already accepted under the new schema until a compatible writer completes them. Disable automated historical adoption if conflicts rise. No full-database rewrite is required.
4. **Acceptance by boundary.** Native registry resolves exact pins and archived extensions. Job tests admit exploratory scored and unscored runs, reject partial declared hypotheses and late changes on open Jobs, and exercise all submission/retry paths. Producer tests cover multiple outputs in one Attempt, count zero vs missing, split leakage, channel-unit mismatch, and two calibration revisions in one collection. Publication checks a valid negative result, undefined denominator and retry after a verified report arrives. Catalog/MCP/UI agree on the same source digest, conflict and primary metric. Firefox tests list/detail, drill-down, narrow viewport and selection-preserving refresh. Historical fixtures cover ambiguous parents, stale concurrent adoption and idempotent replay. Final isolated end-to-end run follows one derived Dataset through a selected Policy to a case, then repeats with a descriptive evaluation and no declared hypothesis.

The prototype demonstrates navigation and evidence interpretation. Implementation acceptance requires the admission, publication, cross-client and reconciliation checks above.
